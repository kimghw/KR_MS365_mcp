# 멀티유저 구현 재검토 (astra)

## 요약 판정

**현재 상태로는 출시 불가다. 확인된 High 이슈가 2건 있다.** 키 폐기 전에 대기열에 들어간 요청이 **폐기 완료 후 새로운 Graph 변경 요청을 전송**하며, Outlook의 제한 없는 `top` 값은 작은 요청 하나로 공유 서버의 자원을 고갈시킬 수 있다. 직접적인 A→B 토큰 선택, 도메인 저장소의 `owner_key` 조건 누락, mode 1의 기본 사용자 폴백은 발견하지 못했지만, OAuth 동시 완료·계정 삭제·부분 성공 오류 정화·마이그레이션 검증에도 결함이 남아 있다. 미커밋 diff와 관련 신규 파일을 읽고 일부 경합을 메모리 내에서 재현했다. 파일은 수정하지 않았으며, 제공된 **1236 passed, 4 skipped** 및 프로세스 스모크 결과를 참고했으나 pytest와 실제 Entra 로그인 왕복을 다시 수행하지는 않았다.

## 테스트 공백

1. **폐기 이후 신규 외부 호출 차단**  
   semaphore·서비스 초기화·refresh lock 대기 중 키 폐기, 만료, disable을 발생시켜 이후 Graph 요청이 **0건**인지 검사해야 한다. 현재의 최종 응답 차단 검증만으로는 외부 변경을 보호하지 못한다.

2. **OAuth 동시성의 원자성**  
   같은 사용자의 두 콜백을 토큰 저장과 epoch 확정 사이에서 교차 실행하고, reconnect·disconnect·보상 삭제도 함께 검증해야 한다. 병렬 start에서도 active attempt가 3개를 넘지 않아야 한다.

3. **삭제·reinstate와 실행 중 작업**  
   여러 프로세스에서 다운로드·변환·DB 저장·열린 파일 handle을 유지한 채 삭제하고 즉시 reinstate하는 테스트가 필요하다. 이전 생애의 작업이 새 사용자 디렉터리나 DB에 저장하지 않아야 한다. worker 반복 취소와 서버 종료도 포함해야 한다.

4. **실제 HTTP redirect 처리**  
   `_request` 대체물만으로는 라이브러리의 redirect 동작을 검증하지 못한다. 로컬 HTTP 시험 서버로 301·302·307·308, 같은/다른 origin, 다른 사용자 nextLink, HTTPS downgrade, 내부 주소, 사전 서명 후속 redirect를 검사해야 한다.

5. **자원 상한**  
   극단적인 `top`이 작업 생성 전에 거부되는지, 파일·폴더·압축 문서의 입력·출력 총량과 변환 시간이 제한되는지 검증해야 한다. 사용자별 동시 실행 수만으로 메모리·디스크 상한을 대체할 수 없다.

6. **오류·로그의 비밀정보 차단**  
   혼합 성공/실패 배치와 중첩 `errors`에 canary를 넣어 검사해야 한다. 실제 Azure SDK 오류, converter/subprocess stderr, debug traceback에도 토큰·이메일·절대경로·OAuth code·verifier·cookie가 남지 않는지 확인해야 한다.

7. **Windows 파일 소비 경로**  
   helper 단위 테스트에 더해 실제 Outlook·Teams 업로드와 FileHandler 변환에서 최종 handle 검증이 유지되는지 검사해야 한다. hardlink·경로 교체·재열기·요청 디렉터리 정리를 포함한다.

8. **마이그레이션 중단·재개**  
   각 rename/journal 경계에서 중단하고 staging/live 변경, 대상 계정 삭제, apply 이후 legacy 쓰기를 주입해야 한다. 정상 재실행뿐 아니라 불일치 상태를 거부하는지도 증명해야 한다.

9. **운영 출시 관문**  
   실제 Entra 로그인 왕복과 계정 불일치·JWKS 갱신, 실제 클라이언트의 매 요청 bearer·stateless 동작, Key Vault 권한·키 교체·백업 복원, HTTPS·ACL 설정은 제공된 스모크로 증명되지 않는다. 현재 고정된 DEK 버전에서 운영 키 교체로 전환하는 절차도 확인이 필요하다.

## 잘 된 점

- Outlook·OneNote·Teams·OneDrive·Calendar·Todo·FileHandler의 mode 1 배선에서 공유 인증 객체·기본 사용자·전역 개인 서비스로 돌아가는 경로를 발견하지 못했다. Time은 무상태 예외로 타당하다.
- HTTP middleware→SDK `request_ctx` bridge→런타임→서비스 lease→handler의 identity 전달은 정상 경로에서 설계와 일치한다. FileHandler도 `copy_context()`로 worker에 컨텍스트를 전달한다.
- bearer 형식·digest·상수시간 비교·만료·폐기·scope 검사, 사용자별 DEK와 AES-GCM AAD, 프로세스 내·간 refresh lock 및 버전 조건 저장이 구현되어 있다.
- OAuth는 시도별 상태·TTL·일회 소비·PKCE·nonce·브라우저 바인딩과 ID token 서명·iss·aud·tid·예상 `(tid, oid)`·Graph `/me.id` 검증을 갖춘다. 이 범위에서 open redirect나 오류 콜백의 전역 Event 간섭은 발견하지 못했다.
- OneNote·Teams·Outlook·FileHandler 저장소의 owner 조건과 사용자별 물리 경로가 일관된다. 마이그레이션도 소유자 불명 데이터를 격리하고 토큰을 이전하지 않는다.
- param_spec 중심의 도구 계약과 정규화 진입점이 유지된다. 신규 handler 업무 기본값 중복 및 신규·수정 소스의 **1,200줄 초과는 발견하지 못했다.** 실제 8개 서버를 통과하는 A/B 통합 검증은 유의미한 기반이다.
