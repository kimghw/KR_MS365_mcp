# 멀티유저 구현 3차 검토 (astra)

## 요약 판정

**현재 작업 트리의 멀티유저 운영 출시는 승인 보류다. 코드 차단 이슈가 남아 있어 “2차 지적 모두 반영” 판정은 수용할 수 없다.** Outlook의 기존 **N01 High 경로인 폐기 후 후속 폴더 생성은 차단**됐다. OAuth disconnect 경합, 마이그레이션 내용 digest, 입력 상한·문자열 검증·응답 정규화·wildcard export도 수정됐다. 그러나 실제 converter가 살아 있거나 서비스 close가 진행 중인데도 drain이 성공하는 경로, FileHandler URL 정책 불일치, migration freeze의 검사·쓰기 경합, Outlook 첨부·누적 저장 제한 누락이 남는다. Outlook 변환 timeout 수정에는 worker 수명 추적이 빠진 회귀도 있다. **이번 검토에서 새로 확정한 High 이상 문제는 없지만, 아래 코드 잔여를 실 Entra·KEK·HTTPS 같은 운영 전 확인 항목으로 대체할 수는 없다.**

검토 기준은 2026-10-23 현재 작업 트리다. 파일을 수정하지 않았으며, 코드 조회와 실제 구현 함수에 메모리 대체물을 연결한 재현을 수행했다. 실 Entra·Graph 호출과 전체 pytest는 실행하지 않았다. **1,510 passed, 4 skipped는 구현팀 보고값**이며 최종 수치는 오케스트레이터 확인 대상이다.

**N03·N04 — drain 완료 판정 재현**

- **N03:** 실제 `_run_converter`·서비스 `_run`·`close`·풀 `drain`을 연결하고 hard cap만 20ms로 축소했다. converter가 대기 중인데 **`drain=True`, `pool.inflight=0`, 살아 있는 converter 1개, 전역 슬롯 점유 1개, cleanup 미실행, `_manager=None`**이었다. thread를 해제한 뒤에야 cleanup과 슬롯 반환이 실행됐다. temp 지연 정리는 개선됐지만, 살아 있는 worker를 삭제용 drain이 계속 추적해야 한다.
- **N04:** 실제 `max_entries=1` 풀에서 B의 lease가 유휴 A를 LRU 퇴거하여 A의 `close()`에서 멈추게 했다. **A의 drain은 True, inflight와 `_closing`은 0인데 close는 미완료**였다. 유휴 `invalidate()`와 drain의 경합도 같았다.
- `drain()`은 최초 `await invalidate()` 뒤에 deadline을 만든다(`service_pool.py:295`–`:296`). 따라서 유휴 close가 멈추면 지정 timeout으로 빠져나오지 못한다.

모든 entry 제거 경로에서 close 시작을 집계하고, 실제 worker·close 완료까지 유지해야 한다. hard cap 초과는 삭제용 drain의 성공으로 처리해서는 안 된다. 실제 사용자 디렉터리 삭제·재생성은 이번에 시험하지 않았다.

**N06·N07 — freeze와 내용 검증은 별개다**

N06에서 lock 대상은 SQLite·JSON 부모와 downloads/output까지 확대됐다. 하지만 `SQLiteStorage.save()`는 guard(`storage.py:126`) 후 연결·INSERT·commit(`:128`, `:135`, `:141`)을 별도 실행한다. JSON도 guard(`:269`)와 파일 open(`:271`) 사이가 분리돼 있다. 기존 OneNote 객체의 `save_item()`과 Outlook `_save_metadata()`에는 쓰기 시 재검사가 없다(`onenote_db_service.py:76`, `:133`; `mail_attachment.py:103`, `:118`).

실제 SQLite 저장 함수·guard를 사용하고 DB만 메모리로 대체해, **guard 통과 직후 freeze 발생을 주입하자 frozen 상태에서 저장 성공·행 1개**를 확인했다. 이미 frozen인 다음 호출은 거부됐다. 완전한 코드 해소에는 모든 writer가 참여하는 상호배제가 필요하다.

N07의 digest는 writer와 동일한 `written_columns`·`row_values`를 사용한다. 레코드 기반 metadata/mail도 실제 INSERT 컬럼과 일치한다. 제외된 `id`는 자동 증가 surrogate ID이고, **`chat_id`, `item_id`, `page_id`, `message_id`, `processed_files.seq/file_ref`는 검증 대상**이다. 명시적으로 제외한 시각 컬럼과 target 기본값까지 포함하는 전체 DB 바이트 검증은 아니다.

실제 `_check_db()`에 정상 메모리 DB는 통과했고, owner·행 수를 유지한 **본문 필드 변경과 Graph ID 변경은 모두 digest 불일치**로 거부됐다. 완료 journal 재호출도 `current_state: unverified`를 명시하며, 현재 데이터 확인은 별도의 `verify --live`로 구분한다.

**N08 — 남은 공개 경로 제한 누락**

1. **특정 첨부 다운로드의 단건 25MiB 제한 누락**  
   공개 `graph_mail_client.py:614`–`:625` → `fetch_specific_attachments()`는 요청 200MiB budget만 확인한다(`mail_attachment.py:777`, `:803`). 단건 상한과 비교하지 않은 채 `:819`, `:826`에서 decode한다. 단건 cap=100, 요청 cap=1000으로 축소한 실제 함수 재현에서 **120바이트가 decode·저장 콜백까지 도달하고 `downloaded=1`**이었다.

2. **사용자 지정 저장 폴더의 누적 quota 누락**  
   요청마다 새 backend를 만들지만(`graph_mail_client.py:124`, `mail_attachment.py:219`), 사용량은 `files/downloads/outlook`만 집계한다(`mail_attachment_user_storage.py:45`). 실제 쓰기는 사용자 `files/` 안의 임의 `save_directory`를 허용한다(`outlook_file_policy.py:78`). 메모리 파일시스템 재현에서 quota=100으로 요청별 80바이트씩 세 번 저장해 **총 240바이트가 저장됐고 스캔 사용량은 0**이었다. 동시성 없이도 발생한다.

3. **decode 예산과 응답 본문 예산의 차이**  
   `response.json()`이 base64 본문을 먼저 읽는다(`mail_attachment.py:550`, `mail_attachment_single.py:94`). 25/200MiB 검사는 전송·JSON 파싱 단계의 메모리 상한을 보장하지 않는다. 실제 OOM은 재현하지 않았다.

FileHandler 로컬 디렉터리는 같은 요청 limits를 하위 처리에 전달하고 `count_file()`을 호출한다(`file_manager.py:157`, `:525`, `:534`). 이 부분은 해소됐다.

## 신규 발견

기존 지적의 잔여는 위 N 번호로 유지한다. 아래는 N08 수정에서 추가된 worker 수명 문제다.

| ID(P01…) | 심각도 | 파일:라인 | 문제 | 시나리오 | 권고 |
|---|---|---|---|---|---|
| **P01** | **Medium** | `mcp_outlook/mail_attachment_processor.py:248`, `:254`, `:298`; `mail_attachment.py:895`; `graph_mail_client.py:1059`; `outlook_service.py:752` | 새 `asyncio.to_thread()`를 `wait_for()`로 제한하지만 **timeout 후 실제 converter thread가 계속 실행되며 사용자별 슬롯·worker 추적·close join이 없다.** | 실제 처리 함수에 대기하는 converter를 연결하고 timeout을 20ms로 축소했다. **순차 호출 3회가 모두 반환한 뒤에도 converter thread 3개가 실행 중**이었다. **가정:** 장시간 종료되지 않는 실제 문서가 있으면 한 사용자가 공유 executor 슬롯을 계속 점유해 다른 작업을 지연시킬 수 있다. 실제 악성 문서·OOM·서비스 중단은 미재현이다. | 실제 worker 종료까지 사용자별 슬롯을 유지하고 close/drain에 연결하거나, 종료 가능한 프로세스 worker를 사용한다. |

기본 executor에는 프로세스 전체 worker 상한이 있으므로 **“무제한 스레드 생성”으로 판정하지 않는다.** 확인된 문제는 timeout 응답 이후의 worker 수명 미추적이다. 이 Outlook 경로에서 temp 조기 삭제가 발생했다고 판정하지도 않는다.

## 운영 전 확인 항목

다음은 배포·운영에서 확인할 사항이다. 위 코드 잔여의 수정과는 별개다.

- **실 Entra 왕복:** 허용 tenant, 예상 `(tid, oid)` 일치, PKCE·nonce·state·브라우저 바인딩, 재연결·연결 해제, 토큰 갱신·JWKS 변경을 실제 계정으로 확인한다.
- **실 MCP 클라이언트:** 매 요청 Authorization 전달, stateless HTTP, 키 폐기·만료 후 동작을 지원 대상 제품·버전에서 확인한다.
- **KEK·복구:** 운영 Key Vault·managed identity 권한, 키 버전 변경, 장애 시 거부, 암호화 데이터 백업·복원을 검증한다.
- **HTTPS·네트워크:** 고정 외부 origin·콜백·인증서·프록시 신뢰 설정을 확인한다. 사전 서명 URL의 검사·연결 간 재해석 한계에 대해서는 실제 egress 정책을 확인한다.
- **파일시스템·ACL:** 단일 호스트 로컬 저장소 배치, 서비스 계정 권한, 다른 OS 사용자 접근 제한, Windows reparse/hardlink 및 열린 handle 동작을 실제 배포 경로에서 확인한다.
- **마이그레이션 운영:** 소유자 매핑과 격리 대상을 확인하고, HTTP뿐 아니라 stdio·백그라운드를 포함한 모든 legacy writer를 이전 전부터 activate 완료까지 실제 중지한다. 활성화 직후 `verify --live`를 실행한다.
- **삭제·유지보수:** 여러 도메인 프로세스를 사용하는 배포에서는 작업 종료 확인 절차를 검증한다. 현재 프로세스의 drain 성공만으로 다른 프로세스 작업 종료를 인정해서는 안 된다.
- **실 Graph 호환성:** Teams chat ID, OneDrive 파일·폴더명, OneNote ID의 퍼센트 인코딩과 실제 upload-session·nextLink·redirect 동작을 실계정으로 측정한다.
- **최종 검증 기록:** 오케스트레이터가 확인한 전체 pytest 수치와 위 잔여 수정의 회귀 결과를 최종 승인 근거에 반영한다.
