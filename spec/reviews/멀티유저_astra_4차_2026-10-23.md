# 멀티유저 구현 4차 검토 (astra)

## 요약 판정

**승인 보류 — 코드 차단 이슈가 남아 있다.** N01·N05는 해소됐고, N06·N08의 지정 보완도 구현됐다. 그러나 N03·N04는 **실패한 close의 기록을 다음 drain이 지우거나, 제거된 항목을 아직 집계하지 않아 drain이 잘못 성공하는 경로**가 남는다. P01에는 **슬롯 획득 대기 중 취소로 사용자 변환 슬롯이 반환되지 않는 회귀**도 확인됐다. ④의 교차 프로세스 drain·thread 강제 종료 불가·동결 상호배제·DNS rebinding·모듈 사본·Graph 실측 잔여는 명시된 운영 조건 아래 설계상 한계로 수용할 수 있지만, **현재 프로세스의 drain 오판정과 슬롯 누수까지 수용된 한계로 볼 수는 없다.** 특히 ④의 lease 유지·drain 실패 보장·동결 후 쓰기 건수 설명은 실제 코드보다 강하다.

검토 기준은 2026-10-23 현재 작업 트리다. 파일을 수정하지 않았으며, 코드 대조와 실제 구현을 사용한 메모리 재현을 수행했다. 재현에서는 파일시스템·HTTP·DB 등 외부 경계를 대체하고 필요한 timeout만 축소했다. 전체 pytest **1,529 passed, 4 skipped는 오케스트레이터 확인값**이며 이번 검토에서 재실행하지 않았다. 실 Entra·실 Graph 미검증 상태는 동일하다.

**N03·N04 — drain 성공 오판정 재현**

1. **close 실패 후 재시도**

   실제 Outlook converter를 Event에서 대기시키고 변환 timeout·close hard cap을 각각 0.01초로 줄였다. 실제 변환 함수·worker 모듈·`MailService.close()`·서비스 풀을 연결한 결과는 다음과 같다.

   ```text
   변환 결과                    conversion_timeout
   첫 번째 drain                False
   즉시 재시도한 두 번째 drain  True
   service.close 호출 횟수      1
   살아 있는 converter thread   1
   점유 슬롯                    1
   pool.inflight                0
   ```

   원인은 `service_pool.py:312`의 `_close_failed.discard(user_key)`다. 실패한 entry는 이미 풀에서 제거됐고 `closed=True`이므로 재시도 시 종료 상태를 확인할 대상도 유지하지 않는다. **invalidate가 먼저 close 실패를 기록한 경우에는 첫 drain부터 True**가 되는 것도 확인했다.

   삭제 경로는 drain이 False일 때 중단하지만, True이면 사용자 디렉터리 삭제로 진행한다(`session/registry_admin.py:394`, `:403`, `:420`). 실제 디렉터리 삭제는 수행하지 않았다.

2. **TTL 일괄 제거의 뒤 항목 미집계**

   A·B의 유휴 entry를 TTL로 함께 제거하고, 먼저 처리되는 A의 `close()`를 대기시켰다. 그동안 B에 대해 **`drain=True`, `inflight=0`, B의 close 시작·완료 모두 False**였다.

   `_close_tracked()`는 전체 제거 목록을 먼저 등록하지 않고 `for entry` 안에서 현재 항목만 집계한다(`service_pool.py:169`–`:174`). 따라서 “모든 제거 경로가 이 함수를 호출한다”는 사실만으로 모든 제거 항목이 추적되지는 않는다.

3. **doomed 수집 뒤 예외**

   TTL 만료 A를 수집한 뒤, 사용 중인 invalid B의 재lease가 거부되도록 구성했다. `:229`에서 A는 풀에서 제거됐지만 `:233`의 예외 때문에 `:251`의 close에 도달하지 않았다. **A의 close는 시작되지 않았고 A의 drain은 True**였다.

4. **close 도중 호출 task 취소**

   B의 lease가 A를 LRU 퇴거한 뒤 A의 close에서 대기하는 동안 B task를 취소했다. **A의 close 미완료인데 A drain=True**였고, B에는 lease 1개가 남았다. `CancelledError`는 `:152`의 `except Exception`에 잡히지 않지만 `_close_tracked`의 finally는 집계를 제거한다. 또한 doomed close 대기는 lease 정리용 `try/finally` 앞에 있다(`:251`, `:254`).

단일 유휴 close에 대한 timeout 수정 자체는 작동했다. 0.03초 drain은 약 0.031초에 False로 반환했고 close 집계는 유지됐으며, close 종료 뒤에는 True였다. **남은 문제는 실패·일괄 제거·예외·취소 경로의 추적 지속성이다.** 실패한 entry를 보존해 실제 종료를 재확인하고, 제거와 전체 close 등록을 같은 임계구역에서 수행하며, 요청 취소와 독립적으로 정리를 완료하도록 보완해야 한다.

**N06·N08 — 보완 효과와 한계**

- OneNote의 frozen 상태 쓰기 5곳은 모두 **DB 연결 0회**로 거부됐다. Outlook도 파일 open 전에 `legacy_store_frozen`으로 중단됐다. 반면 guard 통과 뒤 freeze를 주입한 동시 OneNote writer 2개는 **둘 다 freeze 이후 INSERT 경로를 완료**했다.
- 특정 첨부의 단건 cap을 100, 요청 cap을 1000으로 설정했을 때 120바이트 첨부는 **`attachment_too_large`, decode 0회·저장 0회**였다.
- `_scan_usage()`는 `paths.files`를 시작점으로 downloads·사용자 지정 폴더·uploads의 일반 파일을 모두 집계했다. 초과 Content-Length를 전달한 단건 조회는 **`response.json()` 호출 0회**로 거부됐다. 헤더 없는 응답의 전체 읽기는 여전히 남는다(`outlook_security.py:311`–`:319`).

**④ 잔여 설명의 정확성**

- **변환 worker 종료 — `spec/spec_멀티유저.md:1227`:** “temp·lease·슬롯은 thread 종료까지 유지”는 부정확하다. FileHandler temp와 정상적으로 시작된 converter의 슬롯은 지연 유지되지만, **lease는 Outlook 변환 timeout 후 또는 FileHandler hard cap 이후 반환될 수 있다**(`mail_attachment_processor.py:83`, `:87`; `mcp_file_handler/service.py:261`; `service_pool.py:276`). 이를 보완할 drain 실패 보장도 현재 재시도 경로에서 깨진다.
- **동결 상호배제 — `:1228`:** 상호배제가 없다는 설명과 모든 writer 정지 절차는 정확하다. 다만 “진행 중 쓰기 1건”은 **“표식 생성 전에 검사를 통과한 진행 중 쓰기들”**로 고쳐야 정확하다.
- **worker 사본 — `:1230`:** 두 `conversion_workers.py`의 실행 제어·자료구조·슬롯 로직은 동일하다. 엄밀히는 주석뿐 아니라 `:106`의 로그 문구도 다르므로 “주석만 다름”은 부정확하다. 기능 차이는 확인하지 못했으며 사본 유지보수 잔여는 수용 가능하다.
- 교차 프로세스 drain, DNS 주소 고정 부재, Graph ID 실측 미완료는 이번 수정으로 해소된 항목이 아니다. 기존 운영 조건과 확인 의무를 유지해야 한다.

## 운영 전 확인 항목

3차 목록에서 변경·추가할 사항만 기재한다.

- **삭제·유지보수 검증 강화:** close 실패 후 drain 재시도, drain 전에 발생한 close 실패, TTL 일괄 제거, doomed 수집 후 예외, close 중 취소를 승인 전 회귀 검증에 추가한다. 현재 drain의 True만으로 해당 프로세스 작업 종료를 인정할 수 없다.
- **변환 취소 복구 추가:** 슬롯 포화 상태에서 대기 요청을 취소하고 기존 worker를 종료한 뒤, 슬롯이 모두 반환되고 새 서비스에서도 변환이 가능한지 확인한다.
- **첨부 제한 보장 범위 갱신:** Content-Length 사전 거부가 추가됐음을 기록하되, 헤더 없는 응답의 읽기·JSON 파싱 메모리 상한까지 보장한다고 표기하지 않는다.
- **최종 검증 기록 갱신:** 전체 pytest는 오케스트레이터 확인값 **1,529 passed, 4 skipped**로 갱신한다. 이 통과 기록과 별개로, 위 재현 경로의 수정·회귀 검증 결과가 최종 승인 근거에 추가돼야 한다.
