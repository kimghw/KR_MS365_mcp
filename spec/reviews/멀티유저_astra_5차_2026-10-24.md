## 요약 판정

**(A) main 병합 판정 — 병합 가능.** 요청한 범위에서, **병합 후 mode 0을 유지하고 mode 1을 활성화하지 않는 전제**다. Q01은 mode 0에서도 해소됐다. 아래 풀 결함은 mode 1 경로에 해당한다. mode 0은 전역 서비스를 직접 사용한다(`mcp_common/runtime.py:218`, `mcp_common/service_context.py:65`).

**(B) mode 1 출시 승인 판정 — 승인 보류.** N03·N04-c에 추가 잔여가 있고, N04-b 수정에서 **TTL 만료된 동일 키의 닫힌 서비스를 다시 빌려주는 신규 회귀 Q02**를 확인했다. 이번 범위에서 신규 High는 확인하지 못했다.

검토 기준은 **HEAD d348c06**이다. `main` f6c7121의 조상 관계를 확인했다. 파일·git 상태는 변경하지 않았다. 실제 구현을 메모리에서 실행했으며, 파일·DB·HTTP 경계는 대체했다. 전체 pytest는 재실행하지 않았다.

## 재현 결과

**4차 지정 시나리오**

| 시나리오 | 실제 구현 메모리 재현 결과 |
|---|---|
| converter 생존 상태에서 close 실패 후 즉시 drain 재시도 | **False → False**. 실패 entry·생존 thread·점유 슬롯 각각 1 유지. converter 종료 후 **True**, 모두 0. |
| drain 전에 invalidate가 먼저 close 실패 기록 | 동일하게 **False → False → 종료 후 True**. |
| TTL로 A·B 일괄 제거, A close 대기 | B close도 대기시키면 **A·B inflight 각각 1**, B drain **False**. B 종료 후 성공. |
| doomed 수집 뒤 예외 | 기존 invalid B 시나리오는 수집 전에 거부되어 A가 풀에 남는다. 별도로 용량 축소를 주입해 수집 후 `overloaded`를 발생시켜도 A close가 완료됐다. |
| A 퇴거 close 중 B 요청 취소 | A close 추적 유지, B lease 수 **0**. 다만 B 재요청 복구에는 아래 잔여가 있다. |
| 슬롯 상한 1에서 대기 요청 취소 → 기존 슬롯 반환 → 새 서비스 변환 | `owner_key=None`과 사용자 키 모두 **슬롯 0·새 서비스 변환 성공**. 반복 취소도 동일. |

N03 통합 재현은 실제 `UserServicePool`, `convert_with_deadline`, `MailService.close` 본문, `WorkerGroup`, converter thread를 연결하고 timeout만 축소했다. FileHandler도 생존 worker가 있으면 반복 close가 실패하며 manager를 유지하고, 종료 후 재시도에서 정상 정리됐다.

**N03 추가 잔여 — 동시 drain의 성공 오판정**

먼저 invalidate로 실패 entry를 만든 뒤, 같은 사용자에 대해 drain 두 개를 동시에 실행했다.

```text
첫 번째 drain          close 재시도 대기 중
두 번째 drain          True 반환
pool.inflight          1
close 완료             False
사용자 admission 차단  해제됨
```

`:353`에서 실패 목록을 꺼낸 뒤 `:359`에서 재등록을 기다리는 사이 다른 drain이 빈 목록을 관찰한다. 마지막 판정은 실패 목록만 검사하므로 진행 중 close를 놓친다. 한 호출의 finally가 공용 `_draining` 표식도 제거한다.

따라서 사양서 `spec/spec_멀티유저.md:1307`의 “생존 thread가 있으면 drain False”는 **순차 재시도에는 맞지만 동시 호출까지 보장하지 못한다.** 삭제 경로는 False일 때만 중단하므로 의미 있는 잔여다(`session/registry_admin.py:394`).

**N04-c 추가 잔여 — 생성 전 취소 후 복구 불가**

`max_entries=1`에서 B가 A를 퇴거하고 A close를 기다리는 동안 B를 취소했다.

```text
B leases                         0
B ready.done()                   False
B created                        False
A close 완료 후 B 재요청          외부 wait_for(0.03)에서 TimeoutError
다른 키 재요청                    overloaded
```

B는 생성되지 않았지만 캐시에 남는다. `ready` 대기는 슬롯 획득 timeout보다 앞에 있고, 미완료 entry는 TTL·LRU에서도 제외된다(`mcp_common/service_pool.py:130`, `:140`). 취소 뒤 lease 수만 0으로 만드는 것으로는 복구되지 않는다.

**Q01의 mode 0 영향과 폴링 비용**

실제 mode 0 첨부 경로는 명시적 `LEGACY_KEY`를 전달한다(`mcp_outlook/mail_attachment.py:240`). `None`도 같은 registry 키로 매핑되므로 보장은 동일하다.

- 슬롯 포화 중 대기 요청 6개 취소, 기존 worker 종료, 새 서비스 변환까지 성공했다.
- future 생성·worker 등록·`Thread.start()` 실패를 각각 주입해 두 키 모두 슬롯 반환을 확인했다.
- **여유 슬롯이 있으면 sleep하지 않는다.** 간단한 변환 15회 실측 중앙값은 약 0.28ms였다.
- 경합 중에는 10ms sleep과 OS 스케줄링만큼 재개가 늦어진다. 이 Windows 환경에서 슬롯 해제 후 결과까지 약 **16ms**, 50ms 대기 timeout은 약 **64ms**였다. 10ms를 엄격한 지연 상한으로 볼 수는 없다.
- 대기는 `asyncio.sleep`이므로 busy wait가 아니다. 기본 4슬롯·64요청 합성 검사에서는 교착이나 처리량 저하를 관찰하지 못했다. 다만 지속 경합에서 아주 짧은 변환의 처리량은 폴링 간격 영향을 받을 수 있다.

## 신규 발견

**Q02 — Medium: 동일 키의 TTL 만료 후 닫힌 서비스 재사용**

근거: `mcp_common/service_pool.py:252`, `:256`, `:281`, `:291`.

N04-b 수정으로 entry 조회가 TTL 수집보다 앞섰다. 조회한 entry가 바로 다음 수집에서 제거돼도 지역변수는 남으므로 새 서비스를 만들지 않고, 기존 서비스를 닫은 뒤 다시 반환한다.

기본 TTL 600초를 사용하고 메모리 시계만 601초로 전진시킨 결과다.

```text
반환 서비스가 기존 객체인가     True
service / token closed          True / True
factory 호출                    1
실제 lease 중 pool.inflight     0
실제 lease 중 drain             True
```

수집 후 조회 순서만 메모리에서 복원하면 **새 서비스 생성·닫히지 않은 객체 반환·inflight=1**로 바뀌었다. 수정 순서에서 발생한 회귀임을 확인했다. 기존 TTL 테스트는 다른 사용자로 재요청하므로 이를 놓친다(`mcp_common/tests/test_security_contracts.py:381`).

권고는 무효 항목의 사전 거부를 유지하되, **수집 후 실제 캐시에서 entry를 다시 조회**하는 것이다. 동시 drain과 생성 전 취소 문제는 각각 N03·N04-c 추가 잔여로 분류했다.

## 병합·운영 전 확인 항목

- **main 병합:** 제시한 mode 0 유지 전제를 적용한다. 이번 검토는 요청한 다섯 수정과 파급 범위에 한정된다.
- **mode 1 활성화 전 코드:** Q02의 동일 키 TTL 재생성, N03의 동시 drain 직렬화 또는 동등한 추적 보장, N04-c의 생성 전 취소 entry 제거·대기자 해소가 필요하다.
- **회귀 테스트:** N04-b는 실제로 doomed가 생긴 뒤 예외를 발생시켜야 한다. 동일 키 TTL, 같은 사용자 동시 drain, 취소 후 같은 키 재lease 성공, mode 0 슬롯 취소를 추가하고 start 실패 주입 대상을 좁혀야 한다.
- **검증 기록:** `1538 passed, 4 skipped`는 제공된 4차 반영 시점 확인값이다. 이번 메모리 검증이나 현재 HEAD 전체 pytest 통과값과 혼용하지 않는다. ④의 기존 운영 입력 확정 조건은 그대로 유지한다.
